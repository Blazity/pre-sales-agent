# Vercel Workflow Deployment Recovery Design

Date: 2026-05-04

## Goal

Fix the first-launch failure where Slack `/estimate` acknowledges a request but no workflow work runs afterward. The production deployment currently includes the Slack and health API functions, but not the Vercel Workflow runtime functions that execute workflow runs.

This design also covers the adjacent first-launch readiness gaps discovered during setup: project skill discovery, narrow static output, Slack setup details, missing environment variable guidance, and clearer workflow deployment verification.

## Current Failure

The Slack command handler calls `startEstimationWorkflow(...)` and receives a `runId`, so Slack posts "Estimation workflow started!". The deployment does not contain the Workflow coordinator, step executor, or webhook functions, so the accepted run has no deployed runtime path that can execute it.

The current `package.json` build script runs:

```bash
workflow validate --strict && tsc
```

That validates workflow source and type-checks the repository, but it does not emit deployable Workflow functions.

## Recommended Approach

Use Vercel's Build Output API as the deployment artifact format and make the repository build script explicitly emit both function families:

- Workflow runtime functions generated by `workflow build --target vercel-build-output-api`.
- Existing API ingress functions from `api/health.ts` and `api/slack/events.ts`.

This avoids the incomplete one-line fix where `workflow build --target vercel-build-output-api` would emit Workflow functions but replace Vercel's normal API-route auto-detection.

Official context:

- Vercel Workflow runs workflow and step code through Vercel Functions, with queues and managed persistence behind it: https://vercel.com/docs/workflow
- The Build Output API deploys whatever a build command emits under `.vercel/output`: https://vercel.com/docs/build-output-api
- `vercel build` writes build artifacts to `.vercel/output`: https://vercel.com/docs/cli/build

## Scope

In scope:

- Build pipeline changes needed to deploy both API routes and Workflow routes.
- A narrow static output directory for API-only first launch.
- Automated verification of generated deployment artifacts.
- First-launch documentation and skill updates for discovered setup gaps.
- Project-skill adapters so documented `.ai/skills` can be discovered by supported harnesses.

Out of scope:

- Replacing custom MCP servers with in-process tools. That is a separate architecture decision because it conflicts with current repository invariants.
- Fully wiring Vercel Sandbox into the production orchestrator path. This should be handled as either a runtime integration project or a documentation correction after the deployment bug is fixed.
- Fixing empty Pinecone content quality, local `.xlsx` seed conversion, or Vercel CLI sensitive-default behavior.

## Build Pipeline Design

Add a repo-owned build script, for example `scripts/build-vercel-output.ts`, and change `npm run build` to run:

```bash
workflow validate --strict && npm run typecheck && tsx scripts/build-vercel-output.ts
```

The script should:

1. Remove stale `.vercel/output`.
2. Run `workflow build --target vercel-build-output-api`.
3. Preserve the Workflow-generated `.vercel/output/config.json`, diagnostics, and workflow functions.
4. Add deployable functions for:
   - `/api/health`
   - `/api/slack/events`
5. Add or preserve routes needed for:
   - `/.well-known/workflow/v1/flow`
   - `/.well-known/workflow/v1/step`
   - `/.well-known/workflow/v1/webhook/[token]`
   - `/api/health`
   - `/api/slack/events`
6. Add a minimal static output under `public/` and include it in `.vercel/output/static`.

The script should use structured JSON handling for `.vercel/output/config.json` instead of string patching.

## API Function Emission

The implementation should choose the smallest reliable way to emit existing TypeScript API handlers into Build Output API functions.

Preferred implementation:

- Use a bundler or Vercel-compatible builder path that creates `.func` directories with `.vc-config.json` for each API route.
- Keep the route wrappers thin and preserve the existing source modules as the behavior source of truth.
- Ensure required runtime files and dependencies are included.

Minimum generated function set:

```text
.vercel/output/functions/api/health.func
.vercel/output/functions/api/slack/events.func
.vercel/output/functions/.well-known/workflow/v1/flow.func
.vercel/output/functions/.well-known/workflow/v1/step.func
.vercel/output/functions/.well-known/workflow/v1/webhook/[token].func
```

If the Workflow CLI emits a different internal naming layout, the verification should assert deployable route coverage rather than hard-code only one directory shape.

## Static Output

Add a tracked `public/index.html` with a minimal starter landing response. Do not set the repository root as the static output directory.

This prevents first-launch deployment failures such as "No Output Directory named public found" without exposing repository files as static assets.

## Verification

Add a script or test, for example `scripts/check-vercel-output.ts`, that runs after the build and verifies:

- `.vercel/output/config.json` exists and has `version: 3`.
- The Workflow runtime routes are present.
- The health and Slack event API routes are present.
- The required function directories exist.
- `public/index.html` exists and is copied to `.vercel/output/static/index.html`.

Add this check to the required gates through a package script such as:

```bash
npm run check:vercel-output
```

The existing completion gates remain:

```bash
npm run typecheck
npm test
npm run audit:high
npm run scan:secrets
npm run check:mcp-isolation
npm run check:ai-docs
```

## First-Launch Documentation Updates

Update `docs/first-launch.md`, `docs/setup.md`, `docs/deployment/vercel.md`, and `.ai/skills/first-launch/SKILL.md` so setup guidance matches the actual launch path.

Required corrections:

- Document the exact Slack bot scopes:
  - `app_mentions:read`
  - `channels:history`
  - `chat:write`
  - `commands`
  - `files:read`
  - `groups:history` only for private channels
- Document event subscriptions:
  - `message.channels`
  - `app_mention` only after adding and testing an `app_mention` handler; otherwise state that app mentions are not a first-launch trigger.
  - `message.im` only after adding and testing direct-message `!estimate` handling; otherwise state that direct messages are not a first-launch trigger.
- Document the `/estimate` 20-character minimum and that shorter input returns an ephemeral rejection.
- Clarify first launch can work with an empty Pinecone index, but retrieval quality will be poor until seeding is done.
- Document optional seeding and branding variables:
  - `GDRIVE_ESTIMATIONS_FOLDER_ID`
  - `GDRIVE_PROPOSALS_FOLDER_ID`
  - `CASE_STUDIES_BASE_URL`
- Add a workflow deployment smoke check that confirms the deployment includes both API and Workflow runtime functions.

## Skill Discovery Design

Keep `.ai/skills` as the source of truth for repository workflows.

Add harness-specific adapters so users can invoke the same workflows through supported assistants:

- `.claude/skills/first-launch/SKILL.md`
- `.claude/skills/add-mcp-server/SKILL.md`
- `.claude/skills/code-review/SKILL.md`

Each adapter should be short and point to the canonical `.ai/skills/.../SKILL.md` file rather than duplicating the full workflow. If a supported harness cannot follow adapter references reliably, use generated copies and add a drift check.

Docs should then reference registered skill names, for example:

```text
Guide me through setup using the first-launch skill.
```

Avoid duplicating detailed skill instructions in user-facing docs.

## Error Handling And Observability

The build should fail loudly if either function family is missing. A successful build must mean the deployment artifact can run both:

- request ingress through `/api/*`
- workflow execution through `/.well-known/workflow/v1/*`

For runtime observability, the first-launch guide should tell operators to check:

- Slack acknowledgement.
- A Vercel Workflow run exists.
- Workflow progress logs or step events appear.
- Slack thread receives progress or failure output.
- Google Docs and Sheets outputs are created when the workflow succeeds.

## Testing Plan

Add focused tests or scripts for:

- Build Output API config merging.
- Required function route coverage.
- Static output existence.
- Skill adapter coverage for every `.ai/skills/*/SKILL.md`.
- First-launch docs drift for required Slack scopes, events, and environment variables.

Run the full required gates before considering implementation complete.

## Risks

- Build Output API function packaging may miss runtime dependencies. Mitigate by using a bundler or Vercel-compatible builder strategy and verifying with `vercel build` locally.
- Workflow CLI output shape may change. Mitigate by checking route coverage and required behavior rather than depending only on exact generated paths.
- Skill adapter duplication can drift. Mitigate with generated adapters or a static drift check.
- Documentation may continue to overstate Sandbox usage. Mitigate by filing a follow-up architecture decision immediately after this recovery work.

## Open Follow-Up Decisions

- Decide whether custom MCP stdio servers should remain the public starter architecture or be replaced by in-process tools.
- Decide whether Vercel Sandbox should be wired into the production workflow path or removed from the default architecture docs and dependencies.
